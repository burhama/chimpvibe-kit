# ChimpVibe contribute — private Draft to submission

The user's request is the message that invoked this skill (`$ARGUMENTS` when the client substitutes it). ChimpVibe hosts games as code, not submitted links. A submitted Draft is private to its author until the owner accepts it; an accepted revision is not necessarily serving players. Submission completes **your** job; the owner alone reviews and decides on publication/deployment.

## Establish the live contract

1. If the request includes `chimpvibe:<slug>#<n>`, use the `tag` skill to call `chimpvibe_resolve` **first**. Carry forward its result if already resolved. Continue only when the user chose Modify and `actions.modify.call` is available. Historical legacy tags remain readable/installable, not writable. Do not reinterpret a legacy ref as a native revision.
2. Find the ChimpVibe MCP tools actually available in this client (load deferred tools using its discovery facility where applicable). Call `chimpvibe_whoami {}` to verify membership, then `chimpvibe_guide {}` and inspect current `tools/list`. Follow the guide and tool schemas from this serving build over this skill if they differ. If tools are missing, the token is rejected, or native authoring is closed, report the specific condition; direct the user to `https://chimpvibe.dev/join` for their own token or connection setup. Do not ask them to paste a token into chat. A public tag endpoint is not a substitute for authenticated Draft tools.
3. If the user wants a **brand-new independent Game**, use `chimpvibe_new_game` only when it is advertised. Give it a distinct `name` (up to 40 characters), a descriptive `intent`, and a new `requestKey`; its result supplies your private root `draftId`, `game.id`, and scaffold. If the door is closed, explain that nothing was created and wait—do not put the new game into someone else's tree. For a change to an existing Game, use `chimpvibe_games` to select an admitted native Game, then `chimpvibe_tree {slug}` to choose an accepted native ref. `head` means the build serving players and can differ from `latestAccepted`; ask which base when that matters. Do not invent one. Call `chimpvibe_fork_from {slug, ref}` unless `chimpvibe_resolve` already supplied `actions.modify.args`. Its result gives `call: chimpvibe_begin_draft` and exact `slug`/`revisionId`. Fill the intent and a fresh `requestKey` and call it; keep the returned `current.draftId`. Nothing is merged or rebased automatically. If the user's intent is unclear, ask before creating the Draft.

## Edit the exact Draft

4. Call `chimpvibe_draft_status {draftId}` and `chimpvibe_draft_list {draftId}`. Read relevant files with `chimpvibe_draft_read` (read further slices as needed). Preserve the server-issued `id` and `gameId` in `game/manifest.json` exactly, including for a root Game; they are identities, not revision labels. Follow `chimpvibe_guide` for the game runtime/client contract, source policy, multiplayer/privacy and layout rules. Work within `game/`; do not introduce network access, data exfiltration or a sandbox escape.
5. Pick one current editing route from the live guide: exact edit with `chimpvibe_draft_patch`; coordinated edits with `chimpvibe_draft_patch_many` and the status digest; full text file with `chimpvibe_draft_write`, old file hash and exact new UTF-8 hash; larger local tree with the verified bootstrap's `import-draft.mjs`. For local preview, export exact server-owned bytes and use the verified runner from `/authoring/bootstrap.json`; respect its OS isolation requirement. A preview or `chimpvibe_draft_probe` is not public gameplay or publication. Read source and hashes before edits; a mutation invalidates earlier validation.
6. For every new mutation that takes `requestKey`, generate a fresh key (8–100 characters); reuse it only for the *exact same* call after a lost reply. For ambiguous results consult `chimpvibe_draft_receipt {requestKey}` (the original operation) and `chimpvibe_draft_status {draftId}` (current state) before deciding whether anything needs retrying. A changed argument, including corrected content bytes/hash after a `CONTENT_HASH_MISMATCH`, requires a **new** key. Follow returned error remedies; never treat a failed receipt as success.

## Validate and stop at submission

7. Use `chimpvibe_draft_validate {draftId, requestKey:<new key>}` on the current bytes. Confirm its `current.status` and validation match the current content and are fresh; follow the returned `next` and resolve warnings or ask the user about accepting them. Validation is not a browser playtest: for gameplay claims use an isolated local runner and separate actual observations. For a new Game, attach a **real screenshot of it running** before submission (the current guide describes private capture/store, `upload-thumbnail.mjs`, or `chimpvibe_submit_thumbnail` when available). Do not use generated artwork as evidence of play.
8. Call `chimpvibe_draft_submit {draftId, requestKey:<new key>}` only after current validation. On a successful `done: true` result, tell the user: **“Submission complete, there's no more for me to do.”** State that owner review/acceptance is pending and the build is not automatically serving. Stop: no publishing, deployment, push, duplicate submission or polling for acceptance. For a later status request, `chimpvibe_whoami.submissions.native` gives a bounded own-work summary; use `chimpvibe_my_submissions`/`chimpvibe_draft_status` for more detail. Keep Draft status distinct from `serving` (`serving`, `not-serving`, `unknown`); `unavailable` is not zero submissions.
