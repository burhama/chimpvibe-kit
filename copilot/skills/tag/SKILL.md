# ChimpVibe tag — follow the resolved record

The user's message is the request that invoked this skill (`$ARGUMENTS` when the client substitutes it). Find its tag and whether they already chose Install, Ask, or Modify. If there is no tag, ask for one from the game's tree and stop. A tag identifies one immutable build, not necessarily the one serving players.

1. Call the available `chimpvibe_resolve` MCP tool with `{"tag":"<the whole user message>"}` and, when the door is clear, `"door":"install"`, `"ask"`, or `"modify"`. If your client defers tools, discover/load the actual tool first. If the MCP tool is unavailable, the public `GET https://chimpvibe.dev/api/tag/<URL-encoded tag>` can resolve a **published** build without a member token; a private native revision requires authenticated MCP access. If neither works, report what is missing and stop. Never invent a ref, revision ID, host, or package URL.
2. If resolution fails, relay the error and stop. Begin the reply with the returned `gate`. If no door was chosen, print the returned `menu` exactly after the gate and wait for one choice. Do not start another door or a Draft yet. Carry this same resolved record forward when the user chooses.
3. For the selected door use `actions.<door>` and its `next` guidance. The record, not whether `host` or `artifact` is null, decides what is possible:
   - **Install — historical ZIP:** `artifact.zip` identifies an old git archive. Fetch only that URL and verify its `artifact.sha256` before extraction; stop if a trustworthy hash is missing or mismatched. Follow `actions.install.recipe` to install dependencies and start the legacy local server only if requested. Keep it reachable only from loopback (`127.0.0.1`); if the server binds more broadly and you cannot block external ingress, stop before starting it. Never print the operator token from its logs. Its no-Docker instructions apply to this ZIP, not to native games.
   - **Install — native package:** a published native revision has `actions.install.package` (`game-evolve-package/2`) and `actions.install.runner`. Verify the package SHA-256 from the record or response header. Obtain the runner entry and its hash from the same origin's **public** `/authoring/bootstrap.json`, verify it, then follow the returned runner recipe. Published native Install/Ask can use the public resolved actions and bootstrap without authenticated `chimpvibe_guide`; that guide is supplementary when available. Node >= 22.13 and OS isolation are required (macOS built-in sandbox; Linux Docker); keep the runner on loopback and never bypass a refusal to run unsandboxed. An unpublished native revision has no public URL: authenticated `chimpvibe_read_package` describes it and serves verified slices to members. Follow the record's note if installation is unavailable here.
   - **Ask:** read the exact build's source before answering. For a historical ZIP, use its verified archive; for a published native package, unpack its verified JSON envelope and decode its files; for an unpublished native revision, use member-scoped `chimpvibe_read_package`. Cite actual `game/` files, and explain when access is unavailable. Do not infer gameplay from a title or a different revision.
   - **Modify:** proceed only if `actions.modify.call` is available. An admitted native revision supplies `chimpvibe_begin_draft` and `args` with `slug` and `revisionId`; continue with the `contribute` skill using those exact resolved identities, filling only the intent and a fresh request key. If `actions.modify.note` says unavailable, tell the user why and stop. A historical legacy tag is Install/Ask-only; if the Game has an admitted native revision, ask the user to select it separately rather than silently switching bases.

To contribute without a tag, use the `contribute` skill directly. Keep the token private. Installing or asking does not submit anything; a successful Draft submission ends the agent's work. The owner alone reviews and decides whether to accept or deploy, and acceptance does not imply the revision is serving.
